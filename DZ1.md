# ДЗ №1. Выбор проекта, роли, сценарии и требования
**Тема:** 3. Мессенджер  
**Студент:** Кузнецов Игорь Андреевич 

## 1. Выбранная система
Сервис для личного и группового обмена сообщениями в реальном времени с поддержкой истории переписки и индикацией статуса присутствия ("онлайн", "печатает...").

## 2. Роли пользователей
1. **Обычный пользователь (User):** Основной потребитель сервиса. Отправляет и читает сообщения, управляет своим статусом, создает групповые чаты.
2. **Модератор (Moderator):** Сотрудник поддержки. Имеет доступ к инструментам для блокировки спамеров, просмотра жалоб и удаления запрещенного контента по идентификатору сообщения.
3. **Системный сервис (System/Cron):** Внутренняя роль. Отвечает за фоновые задачи: отправку push-уведомлений офлайн-пользователям, очистку устаревших сессий.

## 3. Сценарии использования
1. **ГЛАВНЫЙ СЦЕНАРИЙ: Отправка и доставка личного сообщения в реальном времени.** Пользователь А отправляет текст, сообщение мгновенно появляется у Пользователя Б, и Пользователь А получает статус "Доставлено".
2. **Загрузка истории переписки.** Пользователь открывает чат и подгружает предыдущие 50 сообщений при скроллинге вверх.
3. **Обновление статуса "онлайн" / "печатает...".** Клиентское приложение отправляет heartbeat-сигнал на сервер каждые 5 секунд при активной сессии.
4. **Отправка сообщения в групповой чат (Fan-out).** Пользователь отправляет сообщение в чат на 100 участников, система мультиплицирует его для всех активных получателей.

## 4. Функциональные требования
- **ФТ 1:** Система должна гарантировать доставку личного сообщения от отправителя получателю и возвращать отправителю статус "Доставлено" (Сценарий 1, Роль: User).
- **ФТ 2:** Система должна предоставлять возможность загрузки истории чата (пакетами по 50 сообщений) в хронологическом порядке (Сценарий 2, Роль: User).
- **ФТ 3:** Система должна принимать и транслировать статусы присутствия контактам с интервалом не реже 1 раза в 5 секунд при активной сессии (Сценарий 3, Роль: User/System).
- **ФТ 4:** Система должна поддерживать рассылку одного сообщения всем участникам группового чата (до 100 человек) с гарантией доставки каждому активному участнику (Сценарий 4, Роль: User).
- **ФТ 5:** Модератор должен иметь возможность найти сообщение по ID и удалить его, после чего оно должно быть скрыто у всех получателей (Роль: Moderator).

## 5. Требования к задержке (Latency)
*Все значения указаны для пиковой нагрузки. SLO и алерты строятся по p99.*

| № | Сценарий использования | p50 | p95 | p99 (SLO) | Обоснование |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1** | **Отправка и доставка личного сообщения (ГЛАВНЫЙ)** | < 50 мс | < 150 мс | **< 300 мс** | Критичный для UX сценарий. Значение p99 < 300 мс является индустриальным стандартом для интерактивных API, чтобы пользователь не ощущал "тормозов". |
| **2** | Загрузка истории переписки (50 сообщений) | < 100 мс | < 300 мс | **< 800 мс** | Операция чтения, часто закэширована. Пользователь готов подождать до 1 секунды при скроллинге, строгие требования избыточны. |
| **3** | Обновление статуса "онлайн" / "печатает..." | < 20 мс | < 100 мс | **< 500 мс** | Фоновый heartbeat-трафик. Допускается eventual consistency, поэтому требования к хвостам распределения снижены для экономии ресурсов. |
| **4** | Отправка сообщения в групповой чат (fan-out, 100 чел.) | < 100 мс | < 500 мс | **< 1200 мс** | Операция требует асинхронной мультипликации сообщения (запись в N очередей). Хвост распределения толще из-за вариативности скорости обработки воркерами. |

## 6. Остальные нефункциональные требования (НФТ)
- **Доступность (Availability):** 99.9% времени в месяц (допустимый простой ~43 минуты в месяц). Мессенджер является основным сервисом, такой уровень оставляет разумный error budget для разработки новых фич.
- **Сохранность данных (Durability):** 99.999% для факта записи сообщения. Потеря отправленного сообщения недопустима. Достигается асинхронной репликацией на диск (fsync) и хранением не менее 2-х копий данных перед отправкой ACK клиенту.
- **Согласованность данных (Consistency):** 
  - *Строгая (Strong / Read-your-writes):* для факта отправки/доставки сообщения и истории чата. Пользователь должен немедленно видеть свое отправленное сообщение.
  - *В конечном счете (Eventual):* для статуса "онлайн" и "печатает...". Допустима задержка актуализации до 2-3 секунд, строгая согласованность здесь создаст избыточную нагрузку.
- **Геораспределенность:** Активно-активная архитектура или гео-шардирование с маршрутизацией через GeoDNS. Пользователи находятся в разных регионах, и сетевая задержка (RTT) не должна съедать бюджет latency (например, RTT между Европой и Азией ~150-250 мс). Персональные данные хранятся в соответствии с локальным законодательством, реплицируются только метаданные для маршрутизации.

## 7. Согласованность требований
Требования внутренне непротиворечивы и соответствуют выбранным сценариям:
1. **Разрешение CAP-компромисса:** Мы не требуем строгой согласованности (Strong Consistency) для всех данных. Использование eventual consistency для статуса "онлайн" (Сценарий 3) снижает нагрузку на систему синхронными блокировками, что напрямую поддерживает требование высокой доступности (99.9%).
2. **Соответствие задержек сценариям:** Более высокий порог p99 < 1200 мс для группового чата (Сценарий 4) логично вытекает из необходимости fan-out рассылки, в то время как для личного сообщения (Сценарий 1) сохранен строгий SLO p99 < 300 мс, так как это главный сценарий, определяющий базовый UX.
3. **Геораспределенность и Latency:** Требование гео-шардирования напрямую обосновывает возможность достижения целевых значений p99 < 300 мс для пользователей из разных часовых поясов, так как физический RTT не превышает бюджет задержки.
